# Sendust dependency policy

> Scope: this skill only serves building Sendust — the standalone native email delivery engine (Rust core → native Node-API addon → thin TS facade). Anything else (SMTP server, hosted service, queue, alternate transport, pure-JS engine) is out of scope.

Authoritative source: `docs/engineering/dependency-policy.md` in the sendust repository; version pins live only in `docs/engineering/toolchain-baseline.md`. Applies to every Rust crate, npm package, GitHub Action, and test fixture source.

**See also:** [sendust-crate-and-module-boundaries](../sendust-crate-and-module-boundaries/SKILL.md) for the boundary a dependency must not cross · [sendust-validation-commands](../../quality/sendust-validation-commands/SKILL.md) for the evidence commands · [sendust-evidence-and-gates](../../quality/sendust-evidence-and-gates/SKILL.md) for labeling evidence.

## 1. Direct Rust pins

| Crate | Pin | Kind | Features | Owner crate | Purpose |
| --- | --- | --- | --- | --- | --- |
| `lettre` | `=0.11.23` | normal | `smtp-transport`, `tokio1-rustls`, `ring`, `webpki-roots`, default off | `sendust-core` | only MVP outbound transport |
| `napi` | `=3.16.2` | normal | `napi8`, `async` | `sendust-napi` | Node-API 8 binding |
| `napi-derive` | `=3.7.0` | normal | — | `sendust-napi` | binding macros |
| `napi-build` | `=2.6.0` | build | — | `sendust-napi` | build setup |

- `sendust-core` declares no build script and no binding, runtime, or Node.js dependency.
- `sendust-napi` depends on `sendust-core`, never the reverse.
- `lettre` is declared once at workspace level and must not appear in `sendust-napi`.
- Test-only dependencies (mail-parser for MIME verification, benchmark tooling) are added by the phase that needs them, pinned exactly, recorded with kind `dev`, and never enabled for published artifacts.

## 2. Feature and transitive policy

- lettre's default `pool` and `native-tls` features must never resolve — pooling and connection reuse are outside MVP scope.
- TLS uses the rustls `ring` provider with `webpki-roots`; verification is always on. No configuration, feature, or method that disables it may be added.
- Feature flags are declared once at workspace level; enabling an optional capability per crate to work around a pin is a policy violation.
- A dependency that pulls OpenSSL, `native-tls`, or a second TLS stack blocks the change.

## 3. Lockfiles

- `Cargo.lock` is committed for the workspace, generated by the pinned toolchain in `rust-toolchain.toml`. A lockfile resolved by another toolchain is not evidence.
- CI resolves with `--locked`; never silently regenerate the lockfile in a release job.
- One root `package-lock.json` is authoritative. Do not commit `pnpm-lock.yaml`, `yarn.lock`, or `bun.lockb`.
- No dependency is installed by a postinstall script; no native binary is downloaded at install time.

## 4. npm development tool pins (exact, no ranges; enforced by `scripts/check-docs.mjs`)

npm 12.2.2 · TypeScript 7.0.2 · Biome 2.6.7 · Vitest 5.1.0. Development tools never ship to consumers and install from one root lockfile.

## 5. Prohibited capabilities (regardless of which crate provides them)

- A custom SMTP protocol stack or SMTP parser — lettre is the only implementation.
- Insecure TLS toggles, plaintext fallback, certificate/hostname bypass.
- URL, HTTP, or remote attachment fetching.
- Connection pooling, automatic retry, internal queues, workers, schedulers, persistence.
- A third Rust crate, extra workspace, plugin registry, or alternate transport.
- Node.js, `napi`, or JavaScript runtime types inside `sendust-core`.
- SMTP, MIME, validation, or delivery policy inside `sendust-napi` or `ts/src`.
- `any` in public TypeScript contracts.
- Telemetry or observability SDKs that could carry message content or credentials.

## 6. Adding a dependency — required steps

1. State the requirement or constraint ID that needs it, and why stdlib and existing pins cannot satisfy it.
2. Check license compatibility and record the license, version, and source.
3. Check maintenance status, release cadence, advisory history, and transitive weight.
4. Confirm it does not cross the core/binding boundary, add runtime-specific behavior to shared code, or duplicate SMTP/MIME/validation policy.
5. Pin the exact version and the smallest feature set; verify `cargo tree -e features` and `cargo tree -d`.
6. Update dependency policy, toolchain baseline (if a pin changes), the owning phase plan, and `Cargo.lock` in the same change.
7. Add the license to the inventory and re-run the architecture and documentation checks.

A dependency without a recorded justification is rejected in review even if it compiles.

## 7. Allowed licenses

Pre-approved for direct dependencies: Apache-2.0, MIT, BSD-3-Clause, ISC, Unicode-3.0, CDLA-Permissive-2.0. Any other license requires an explicit recorded decision before merge, compatible with distributing the native addon and npm package.
